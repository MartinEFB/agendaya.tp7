The demo records `SIMULATED_NOT_SENT` or injected `SIMULATED_FAILED`; it does **not** perform SMTP delivery or demonstrate a real SMTP outage.

## Boundaries and known ambiguities

1. **US_006:** the story conversation says an occupied-range edit should not apply, while its acceptance scenario calls for affected reservations, reassignment, an email notice and a 24-hour deadline. Submitted TP1 also describes retaining an affected reservation with an `Excepción` label. Per the user's explicit source choice, the demo follows the **acceptance behavior**: update hours, retain the booking as an exception, offer reassignment, and cancel only after deadline if unresolved. The notice is recorded but **not emailed**; self-service works only in the same browser session, and expiry is request-driven rather than background-scheduled.
2. **US_004:** range categories follow its acceptance criteria (`Vacaciones`/`Licencia Médica`), not TP1's combined blocker list. US_003 keeps its separate `Feriado`/`Motivo Personal` categories. A range requires end strictly after start and covers both endpoints, including any weekend dates.
3. **US_010 and fixtures:** the sources do not specify service count or duration. Two static 30-minute types make plural selection observable without introducing event CRUD. The default week and Buenos Aires offset are fixtures. Short valid working ranges may yield no complete slot.
4. **Infrastructure:** local JSON and optional cloud Redis are mock/persistence choices allowed by TP6, not proof of production durability or privacy compliance. Administration has **no authentication**. No real emails, video room, payment, or cross-browser/performance certification exist. Only fictional guest data should be used.
